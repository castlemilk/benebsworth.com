A database can finish a write quickly and still have substantial work left to do. In an LSM-tree, that work includes merging the sorted files produced by earlier writes. A B-tree maintains a single sorted tree as changes arrive, with page updates and occasional splits. Comparing the two means accounting for both the foreground operation and the work that follows it.

Let's work through their layouts, then use read, write and space amplification to describe the costs. These are two common families of storage structures. Databases also use other layouts. A database may use several structures, and its transaction model adds another layer.

## Two ways to put a tree on a disk

Storage devices transfer blocks, so changing a small value can involve much more data than the value itself. Database page sizes are often measured in kilobytes. Random access is especially costly on spinning disks. Batching can also help SSDs by reducing request overhead and making better use of bandwidth.

A page-oriented B-tree keeps keys in a sorted tree. A lookup follows a path from the root to a leaf. An insert finds the appropriate page, changes it and splits nodes if necessary. A buffer pool can keep these pages in memory and combine several changes before writing them out.

An LSM-tree batches writes in memory and flushes sorted files to storage. Each file is ordered, but key ranges can overlap across files. Reads must resolve these runs and their versions. **Compaction** merges runs to limit the work of future reads and reclaim obsolete entries.

<Callout type="thinking" title="Start with the workload">

Before choosing an engine, ask which operations need predictable latency. Are writes mostly new keys or repeated updates? Do reads fetch individual keys or scan ranges? How much memory and spare storage can you provide? The layout matters, but so do the cache, durability settings and time available for background work.

</Callout>

## The B-tree: update-in-place, shallow, read-optimised

A B-tree node holds many keys and child pointers. The large **fan-out** keeps the tree shallow. Database indexes commonly use the B+tree variant, with entries at the leaves and internal nodes used for navigation. Here we'll use B-tree for the family, while the simulator shows a small classical B-tree.

With effective fan-out $B$ and $n$ keys, the height grows approximately as:

<Equation id="eqn:btree-height" number="1" caption="Large fan-out keeps a tree shallow. This is a height estimate, not a count of physical disk reads." latex="h \approx \log_B(n)">

$$
h \approx \log_B(n)
$$

</Equation>

For a billion keys, $\log_2(10^9) \approx 30$, while $\log_{500}(10^9) \approx 3.3$. The latter suggests a tree only a few levels deep. The exact height depends on leaf capacity, occupancy and how height is counted. It does not guarantee that finding a row takes 3 physical reads: upper levels may already be cached, and fetching the row may require another structure.

<Callout type="info" title="Pages, comparisons and physical reads">

Searching within a cached page involves memory accesses. Loading an uncached page requires storage I/O. Keeping many keys in each page reduces the number of pages along a search path, but a warm cache can make physical reads much lower than tree height. Keep those measurements separate when comparing engines.

</Callout>

In the left pane, insert keys until a node fills. The simulator splits full nodes on the way down, promoting a median key into the parent. A root split adds a level. Other B-tree implementations may split after insertion, and B+tree leaf splits handle separator keys differently, but all must preserve ordering and a balanced tree.

A small change can dirty a whole page. Splits can dirty several. The **page writes** counter illustrates that extra work, not the number of device writes a real database would issue. Logging, dirty-page batching and checkpoints determine when those writes happen. Even the phrase "update-in-place" needs care: it describes a page-layout strategy, not a promise that every SQL update edits the existing row bytes. We'll return to PostgreSQL below.

## The LSM-tree: append to a memtable, flush, compact

A typical durable LSM write goes to a write-ahead log and a memtable. The log supports recovery. The memtable maintains an ordered view of recent entries and eventually flushes to an immutable **sorted string table (SSTable)**. Durability still depends on when the log is synchronised and when the database acknowledges the write.

Updating a key adds a newer version. Deleting one adds a **tombstone**, which hides the older value. Readers combine the memtable and relevant files according to version and visibility rules. Indexes, Bloom filters and caches can eliminate many file or block reads.

Compaction merges sorted runs and may discard superseded entries. It cannot discard every old version immediately: snapshots may still need one. A tombstone must also remain until dropping it cannot expose an older value elsewhere. These constraints are part of the engine's correctness, not just its cleanup policy.

<PullQuote>Immutable SSTables make file contents stable for readers. The engine still has to coordinate which files and versions each reader can see.</PullQuote>

Use **Insert ×8** to fill the 4-key memtable and create L0 runs. In this model, 3 L0 runs trigger a merge with any existing L1 run. That fixed, two-level rule shows flushing and merging. It is not a full implementation of either production tiered or leveled compaction.

The **SSTable writes** counter counts output runs, not bytes written. One large compaction output can contain much more data than one small flush. This is why counting files alone cannot tell us write amplification. Background activity after a burst of inserts can be legitimate compaction work, though compaction is only one possible cause of unexpected I/O.

<Callout type="success" title="What immutability simplifies">

Readers can use an SSTable without coordinating edits to its contents. The database still needs synchronisation around memtables, snapshots and the set of live files. Old files must remain available until no reader needs them. Immutability removes one source of races. The rest of the engine still needs concurrency control.

</Callout>

## The three amplifications and the RUM conjecture

Amplification compares the work or storage used with a useful baseline. Define that baseline before quoting a number:

- **Read amplification:** for a non-empty query result, bytes read from storage divided by bytes returned. For missing-key lookups, count block or run probes instead: dividing by a zero-byte result is not useful.
- **Write amplification:** bytes written at a stated layer divided by logical bytes written by the application. Say whether the measurement includes the write-ahead log, compaction or the SSD's internal writes.
- **Space amplification:** storage occupied divided by the size of live data. Page slack, old versions and temporary compaction output can all contribute. Compression and the definition of live data affect the ratio.

There is no fixed sum of these ratios. A cache or a changed workload can alter them substantially, and a lower byte count does not necessarily mean lower latency.

For classic **leveled compaction**, a common rough cost model uses the number of levels $L$ and their size ratio $T$:

<Equation id="eqn:lsm-write-amp" number="2" caption="A simplified order-of-magnitude estimate for classic leveled compaction. Actual write amplification depends on overlap, workload and compaction policy." latex="W_\text{LSM} \approx L \times T">

$$
W_\text{LSM} \approx L \times T
$$

</Equation>

Compacting data into a larger level can rewrite overlapping data already there. RocksDB's [compaction guide](https://github.com/facebook/rocksdb/wiki/Compaction) describes per-level write amplification approaching the size ratio in the worst case, but often lower in practice. Its compactions select overlapping files rather than necessarily rewriting a whole level.

Putting $L = 5$ and $T = 10$ into this simplified model gives 50. That is an illustrative estimate, not a prediction for every byte or a result measured by the simulator. Ordered inserts, skewed updates and compaction policy can change the result. Tiered compaction has a different cost model. Large sorted outputs encourage sequential I/O, but that does not mean every write through the database, filesystem and device is sequential.

The **RUM conjecture** names the broader tension between read cost (R), update cost (U) and memory or storage overhead (M). Its authors conjecture that optimising two areas negatively affects the third. The following is a schematic reminder of that proposed trade-off, not an algebraic identity or a proven universal bound:

<Equation id="eqn:rum" number="3" caption="Schematic of the RUM conjecture, not an algebraic identity or a proven universal bound." latex="\min R \;\wedge\; \min U \;\Longrightarrow\; \uparrow M \qquad \text{(RUM conjecture)}">

$$
\min R \;\wedge\; \min U \;\Longrightarrow\; \uparrow M \qquad \text{(RUM conjecture)}
$$

</Equation>

Larger Bloom filters can reduce unnecessary LSM reads while consuming memory. More compaction can reclaim stale data while writing more bytes. RUM is a useful framework for asking where a design spends resources. It is not a conservation law, nor proof that one implementation cannot improve on another in several measurements.

<Callout type="warning" title="Read the benchmark conditions">

Compare dataset size, cache budget, key distribution and durability settings. Include a sustained run long enough for background work to matter. Report tail latency alongside throughput and bytes written. A short write burst that finishes before compaction catches up tells us little about steady-state capacity.

</Callout>

## Who picks what, and why

**PostgreSQL** commonly uses B-tree indexes, but stores table rows separately in a heap. An ordinary index lookup can therefore require a heap fetch. An index-only scan can avoid that when the index covers the query and visibility information permits it. Updates create new row versions under multi-version concurrency control (MVCC). A heap-only tuple (HOT) update can avoid new index entries when its conditions hold, including space on the same heap page.

**MySQL/InnoDB** has a different organisation: its clustered index stores row data, usually ordered by the primary key. A secondary index contains the primary key, which can be used to look up the clustered record. Calling both databases "B-trees" hides this important difference in the read path.

**RocksDB** provides an embedded LSM-based key-value engine. Its compaction style, filters and cache are configurable, so even two RocksDB applications can have quite different amplification profiles. **Cassandra** also uses memtables and SSTables, with compaction choices that depend on workload and data lifetime. Neither choice removes the need to budget for maintenance I/O.

```python
# PostgreSQL: an index may locate the row, but UPDATE creates a new
# heap tuple version. HOT can avoid new index entries when eligible.
db.execute("UPDATE accounts SET balance = balance - 100 WHERE id = 42")

# RocksDB: put adds a newer value. Existing SSTables remain immutable.
# This is a replacement value, not the same transactional SQL operation.
store.put(b"account:42:balance", b"...")
```

These calls illustrate storage behaviour, not equivalent account-update implementations. The API alone does not tell us how versions, logging or isolation work.

<Callout type="info" title="Engines combine techniques">

The SQL interface does not determine the storage layout. MyRocks, for example, uses RocksDB under MySQL. Buffered trees and copy-on-write trees provide other ways to manage updates. Keep the data structure, transaction implementation and query interface separate when reasoning about a database.

</Callout>

## The same shape in other rooms

Append-and-clean designs turn up outside database indexes too. A **log-structured filesystem** writes changes into segments and later cleans them to reclaim space. An SSD's **flash translation layer** can map a logical overwrite to a fresh physical page, then reclaim erase blocks through garbage collection. These share the idea of relocating data and cleaning up later, without being the same structure as an LSM-tree.

That SSD layer is a useful complication: a database page update need not overwrite the same physical flash location. Database-level and device-level write amplification are different measurements. Improving one does not automatically improve the other.

**Apache Kafka** provides another comparison. Its partitions are append-only logs, and topics configured for log compaction can reclaim superseded records by key. This is not the same as maintaining sorted SSTables for key lookups. Similar cleanup work serves a different data model.

For a practical engine comparison, I'd start with the operations the application actually performs, then measure the foreground latency and background work together. The small model here helps explain why that work exists. The next step is checking how the chosen engine handles it with realistic data, cache limits and sustained load.

## Reading further

- [Bayer & McCreight, *Organization and Maintenance of Large Ordered Indices* (1970)](https://dl.acm.org/doi/10.1145/1734663.1734671): the original B-tree paper, presented at SIGFIDET in 1970 and expanded in *Acta Informatica* in 1972.
- [O'Neil, Cheng, Gawlick & O'Neil, *The Log-Structured Merge-Tree (LSM-Tree)* (1996)](https://www.cs.umb.edu/~poneil/lsmtree.pdf): the original LSM-tree design and its cost analysis.
- [Athanassoulis et al., *Designing Access Methods: The RUM Conjecture* (EDBT 2016)](https://stratos.seas.harvard.edu/publications/designing-access-methods-rum-conjecture): the authors' statement of the conjecture, with a link to the paper.
- [PostgreSQL's index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html) and [HOT updates](https://www.postgresql.org/docs/current/storage-hot.html): the heap/index distinction and conditions for avoiding new index entries.
- [InnoDB's clustered and secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html): how row storage and secondary lookups differ from PostgreSQL.
- [Petrov, *Database Internals* (O'Reilly, 2019)](https://www.databass.dev/): an implementation-level treatment of storage layouts, indexing and compaction.
